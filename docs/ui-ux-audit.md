# 포털 UI/UX 전수 점검

2026-10-23. React 포털의 전체 화면과 공통 모달을 점검했다. 기준 코드는 `37637f0`이며 이번 작업의 실제 기능 변경은 랜딩 페이지와 관련 라우팅 제거다. 아래 개선 항목은 후속 작업 목록으로, 이번에 모두 수정한 것은 아니다.

## 점검 방법과 범위

- 실제 Docker Compose 개발 환경에서 Express·Traefik·BuildKit과 웹/워커/초기화 서비스가 있는 임시 앱을 실행했다. 사용자·도메인·실패 작업은 격리된 검증 데이터다.
- Chromium의 1440/1024/390/320px와 라이트/다크 테마에서 화면 넘침, 모달 경계, 탐색, 로그와 주요 기능을 확인했다. 1440/390px에서는 아래 화면·모달을 합쳐 82개 상태의 스크린샷과 axe-core 검사를 수집했다.
- 정상 동작뿐 아니라 느린 사용자 목록 조회, 조회 실패, 잘못된 비밀번호, 입력 오류, 설정 초안, 로그인 전 딥링크와 키보드 조작을 확인했다. 느린/실패 응답과 저장소 파일 목록은 브라우저 요청을 가로채 재현했다.
- 소스 검토로 각 상태의 원인을 확인했다. 테스트 코드, 스크린샷과 검증 데이터는 `/tmp`에만 두고 커밋하지 않는다.

추가 검토 후보:

- 공개 저장소 URL 입력 중에도 GitHub 상태 조회 오류가 별도 오류로 남을 수 있다(`CreateApp.tsx:250`). 연동이 필요한 경로에서만 관련 안내를 보여주는 편이 명확하다. 이번에는 소스 검토로 확인했으며 실제 GitHub 장애는 재현하지 않았다.
- 앱·도메인 링크가 새 탭으로 열리는 동작을 아이콘/접근 가능한 이름으로 안내한다(`AppCards.tsx:99`, `Domains.tsx:128`).
- 모바일 사용자/도메인 표는 내부 가로 스크롤을 사용하므로 우측 관리 버튼이 첫 화면에 보이지 않는다. 가로 스크롤 안내, 주요 열 고정 또는 모바일 카드 표현을 검토한다.
- 중첩 폼인 Runtime → Compose 출처 → Build 설정은 모바일에서 매우 길다. 고급 항목 접기와 설정 섹션 바로가기를 검토하되 입력값 보존과 재배포 경고 위치를 유지한다.

## 자동 접근성 검사 해석

82개 화면 상태에서 중복을 합치면 검출된 규칙은 3종이다: `color-contrast` 11개 상태(라이트 PC의 DEV 배지), `target-size` 12개 상태(생성 폼), `scrollable-region-focusable` 8개 상태(로그·Compose 예제). 이 숫자는 고유 결함 수가 아니라 같은 UI가 나타난 화면 상태 수다. 스크린샷과 실제 요소 크기·키보드 조작을 함께 확인해 U05/U06/U11에 반영했다.

자동 검사는 화면 읽기 도구, 모바일 실기기, 모든 서버 오류와 데이터 크기를 대신하지 않는다. 이번 점검에서는 전역 가로 넘침, 모달의 화면 밖 이탈, 브라우저 JavaScript 예외는 발견하지 않았다. 긴 로그/표/예제의 의도된 내부 스크롤은 별도로 구분했다.

## 이번에 적용한 랜딩 제거

- `portal/public/landing/index.html`과 `landing.css`를 삭제했다. HTML 안의 포털 링크 생성 스크립트도 함께 제거됐다.
- Express의 `landingPagePath`, 루트 호스트 판별, 포털 오리진 생성, 랜딩 라우터와 루트 딥링크의 301 이동을 제거했다.
- Compose의 랜딩 전용 `portal-root` 라우터를 삭제했다. 운영 포털은 기존 `portal.<도메인>`으로 제공한다. 루트 도메인에는 포털 라우터도 포털로 보내는 리다이렉트도 없어 기본 HTTPS 구성에서는 404가 된다. 공통 HTTP → HTTPS 이동은 유지한다.
- 개발 서버에 직접 접속하는 `localhost:3000`은 `/auth` 또는 로그인된 대시보드를 제공한다. 인증에 필요한 `/auth` 이동과 GitHub OAuth 콜백 이동은 유지한다.
- GitHub 콜백과 호스트 전용 세션을 보존하기 위해 운영 포털을 루트 도메인으로 추가 노출하지 않는다. DNS/TLS·사용자 앱의 라우팅은 유지한다.
- 제거하거나 추가한 환경변수는 없다. `PAAS_DOMAIN`은 포털·앱 도메인 설정에 계속 필요하며 `.env`에서 삭제할 항목은 없다.

## 변경 검증과 한계

- `npm run build`: TypeScript 검사와 프로덕션 번들 생성 성공. `npm test`: 기존 13개 통과. Compose 구성 검사와 `git diff --check` 통과.
- 호스트·로그인 여부·UI 경로 조합 및 삭제한 정적 자산 등 53개 HTTP 검증을 통과했다. Express 직접 접속에서 호스트 간 리다이렉트가 없고, 제거한 `/landing/*`는 404이며 보호된 API는 미로그인 시 401이다.
- 로컬 Traefik에서 운영의 `Host(portal.<도메인>)` 규칙을 HTTP로 적용해 13개 검증을 수행했다. 루트 `/`, `/auth`, 딥링크는 404, 포털은 세션에 따른 `/auth`/React 화면, 사용자 앱은 HTTP 200을 확인했다.
- 별도 브라우저 회귀 검증으로 레이아웃 64개, 실제 로그 163개, 주요 기능 28개, 입력/권한 경계 14개를 확인했다. 환경변수 저장의 실제 재시작 작업은 `done`, 앱은 readiness 확인 후 `running`이었다.
- 컨테이너 기동은 빈 의존성 볼륨에서 `npm ci --include=dev`부터 확인했다. 클라우드 네트워크의 `get.docker.com` 차단 때문에 기존과 같은 `node:22` 기반 도구 마운트 오버라이드를 사용했다. 원본 Dockerfile의 외부 도구 설치와 실제 운영 HTTPS/인증서 발급은 검증하지 않았다.
- 실제 GitHub OAuth/비공개 저장소 연결, 신규 원격 저장소 전체 빌드·배포, 외부 DNS 검증, NVDA/VoiceOver와 모바일 실기기 검증은 포함하지 않았다.

후속 작업은 U01–U08의 작업 맥락 보존·오류 회복·키보드/터치 조작부터 적용하고, 나머지 설명과 설계 기준을 정리하는 순서를 권장한다.
