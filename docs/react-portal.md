# React 포털 전환

## 범위와 설계

로그인과 포털의 모든 대화형 화면을 React + TypeScript로 전환한다. Express API, 세션 쿠키, 기존 화면 주소와 앱 배포 방식은 유지한다. 공개 랜딩 페이지는 정적 페이지로 유지한다.

- `portal/client`: 페이지, 재사용 폼, 공통 UI, API 타입과 실시간 연결을 관리한다.
- Vite가 `portal/dist`에 브라우저 자산을 생성하고 Express가 기존 인증 경로에서 제공한다.
- 사용자 세션, 앱 목록, 작업 목록은 포털에서 공유한다. 입력 중인 폼은 페이지가 소유하며 목록 갱신이 초안을 덮어쓰지 않는다.
- 앱별 화면은 사용자/앱 이름으로 구분한다. 화면을 떠나면 요청, SSE, WebSocket, 타이머와 터미널을 정리한다. 늦게 도착한 응답이 다음 앱 화면에 반영되지 않도록 취소 신호를 사용한다.
- API가 권한을 판정한다. UI도 비밀번호 변경 의무와 관리자 여부를 반영하며 인증 만료 시 로그인으로 이동한다.
- 기존 레이아웃 CSS를 바탕으로 공통 모달, 버튼, 상태 표시를 React 컴포넌트로 재사용한다. 로그와 터미널의 문자열은 HTML로 삽입하지 않는다.

## 보존할 동작

- 생성: GitHub/공개 저장소, 브랜치, 초기 환경변수, Dockerfile/Railpack 빌드와 단일/Compose 런타임.
- 관리: 앱 상태와 서비스 상태, 배포/시작/정지/삭제, 환경변수, 빌드/런타임 설정 저장 및 재배포 경고, 커스텀 도메인.
- 로그: 서비스 다중 선택, 시각순 병합, 선택적 timestamp, Lines 왼쪽의 timestamp 옵션, 기존 Auto/Refresh 버튼, 실시간 작업 로그.
- Exec: 서비스 선택과 터미널, 화면 이동 시 연결 해제. xterm은 npm 번들로 제공한다.
- 계정/운영: 로그인, 비밀번호 변경, 관리자 사용자 관리, 전체 앱과 포털 로그, 작업 재시도/정리.
- 딥링크, 뒤로/앞으로 이동, 모바일 메뉴, 라이트/다크 테마와 저장된 테마.

## 구현 순서와 검증

1. 타입/API/공통 UI 계약과 빌드 설정을 마련한다.
2. 독립 화면을 분담하여 전환하고 루트에서 라우팅, 상태와 생명주기를 통합한다.
3. 기존 동적 DOM 스크립트를 제거하고 빌드/실행 방법을 문서화한다.
4. TypeScript 검사, 프로덕션 빌드, 기존 회귀 검사를 실행한다. 검증용 신규 테스트는 임시 경로에만 둔다.
5. 실제 Express와 Docker 앱을 실행해 API, 로그/Exec 연결, 인증과 주요 폼을 브라우저로 확인한다. PC/모바일과 양쪽 테마에서 넘침, 정렬, 탐색과 연결 정리를 확인한다.

빌드 결과물과 검증용 임시 코드는 커밋하지 않는다. 검증 후 devel에 병합하고 작업 브랜치를 정리한다.

## 중립색 테마 개편

사용자가 선택한 Vercel 계열의 간결한 클라우드 콘솔 방향으로, `client/theme.css`에 자체 스타일을 작성했다. 흑백과 중립 회색, 얇은 테두리, 작은 모서리, 단색 주요 버튼을 사용한다. 색은 실행/대기/오류 상태를 구별하는 데 집중한다. 라이트/다크 테마와 모바일 탐색을 유지하고 대시보드에 New App 바로가기를 추가한다.

Hyunbbai의 기존 P 브랜드와 시스템 글꼴을 사용한다. 테마용 CSS와 자산은 직접 구성하며, Vercel의 로고·전용 글꼴·원본 UI 코드에 의존하지 않는다. 번들에 포함되는 공개 패키지의 라이선스 고지는 빌드 시 함께 생성한다.

## 검증 결과

2026-10-23, Node.js 22와 Chromium에서 React 전환 및 최종 테마를 함께 확인했다. 검증 스크립트와 실행용 데이터는 `/tmp`에 두었으며 저장소에 테스트 코드를 추가하지 않았다.

- `npm run build`: TypeScript 검사와 Vite 프로덕션 빌드 성공. 터미널을 별도 청크로 분리하고 라이선스 고지 파일을 생성했다.
- `npm test`: 기존 회귀 검사 13개 통과. `docker compose --env-file .env.example -f docker-compose.yml config --quiet`와 `git diff --check`도 통과했다.
- 실제 Express 및 임시 Docker Compose 앱으로 로그 조회/SSE, 서비스 다중 선택, 정지/재개, timestamp 위치, 탭 이동 시 연결 정리를 확인했다. Exec은 실제 WebSocket으로 명령 출력과 서비스 전환을 확인했다.
- 브라우저 너비 1440/1024/390/320px에서 라이트/다크 대시보드, 생성, 사용자 관리, 앱 설정과 로그의 가로 넘침을 확인했다. Jobs 모달의 경계, 포커스 복귀, 로그 아이콘 및 Retry/삭제 버튼 정렬, 모바일 메뉴도 확인했다.
- 로그인/인증 만료, 비밀번호 변경 의무, 관리자 접근 제한, 사용자 추가/삭제, 잘못된 비밀번호의 인라인 오류, 도메인 추가/삭제, 설정 초안 보존, 환경변수 저장 후 실제 재시작, 설정 변경/복원 시 재배포 경고, 작업 재시도와 앱 삭제 후 화면 전환을 확인했다.
- 생성 폼은 요청을 가로채 Dockerfile/Railpack/Compose/환경변수의 API 전송 형식과 늦은 응답이 화면을 바꾸지 않는 동작을 확인했다. 신규 원격 저장소의 전체 빌드·배포는 실행하지 않았다.

GitHub OAuth와 비공개 저장소 접근, 실제 외부 DNS/TLS 인증은 연결 정보가 없어 검증하지 않았다. 재시작/시작 검증의 도메인 readiness는 로컬 HTTP 200 응답기로 제공했다. 공개 랜딩 페이지와 배포 백엔드는 이번 전환 범위에 포함하지 않았다.

## Docker Compose 개발 모드 추가 검증

앞선 검증에서 포털은 호스트의 Node 프로세스로 실행했고, 테스트 앱만 Docker Compose로 실행했다. 이후 `docker-compose.yml`과 `docker-compose.dev.yml`을 함께 사용해 포털·Traefik·BuildKit 전체를 별도 임시 디렉터리와 Compose 프로젝트로 기동했다.

개발 명령이 서버만 감시해 React 파일 수정이 반영되지 않는 문제를 재현했다. `portal/dev.js`가 Vite 빌드 감시와 Node 서버 감시를 함께 실행하도록 수정했다. 최초 타입 검사/빌드는 `predev`가 수행한다. 화면 소스 변경 후 자동 재빌드와 브라우저 새로고침 반영, 서버 소스 변경 후 프로세스 재시작을 확인했다. 종료 신호나 감시 프로세스 종료 시 다른 자식 프로세스도 정리되는지 임시 프로세스 검증을 수행했다.

컨테이너 안의 `npm ci --include=dev`, 타입 검사, 초기 빌드, 개발 서버 기동이 성공했다. 포털 `/health`와 실제 Traefik을 거친 `admin-demo.apps.localhost:18080`의 HTTP 200 응답을 확인했다. 1440/1024/390/320px의 양쪽 테마에서 레이아웃 및 실제 컨테이너 로그 검증도 통과했다. 로그인, 사용자 관리, 설정 저장, Jobs 로그, Exec 서비스 전환, 도메인 추가/삭제도 확인했다. 환경변수 저장 후 재시작 작업은 완료 상태이며, 실제 Traefik readiness 검증 후 앱이 running 상태가 되는 것을 확인했다.

클라우드 네트워크에서 `get.docker.com` 접속이 403으로 차단되어 원본 Dockerfile의 설치 단계는 실행하지 못했다. 임시 오버라이드로 동일한 `node:22` 베이스에 기존 Docker CLI/Compose/Buildx/Railpack 바이너리를 읽기 전용 마운트하고, 클라우드 CA와 Traefik의 로컬 Docker 서브넷 프록시 예외를 제공했다. 애플리케이션 명령·의존성 설치·개발 모드는 저장소 설정을 그대로 사용했다. 이 환경용 설정과 검증 코드는 커밋하지 않는다.

설치 과정의 npm audit은 기존 백엔드 의존성에서 11건(critical 2, high 3, moderate 6)을 보고했다. React 전환 전부터 존재한 Express/Dockerode 계열 등의 잠금 버전이며, 이번 개발 실행 수정에서는 의존성 업데이트나 취약점 재현을 수행하지 않았다.

## 프런트엔드 최신 안정 버전 적용

2026-10-23 npm 레지스트리의 `latest` 태그를 기준으로 프런트엔드 프레임워크와 빌드 도구를 갱신했다. `package-lock.json`에 실제 설치 버전을 고정한다.

| 패키지 | 적용 버전 |
| --- | --- |
| React / React DOM | 19.3.1 |
| React Router DOM | 7.18.4 |
| Vite | 8.3.5 |
| Vite React 플러그인 | 6.1.2 |
| TypeScript | 7.0.2 |
| React / React DOM 타입 | 19.3.0 |

React와 Router는 이미 해당 버전이 설치되어 있었으며 선언한 최소 버전도 맞췄다. Node.js 실행 조건은 유지한다. Vite 설정과 라이선스 생성 플러그인을 `.mts`로 명시하고 `import.meta.dirname`을 사용해 ESM 설정 로딩 경고를 해결했다. `client/vite-env.d.ts`로 CSS 가져오기 타입을 제공하여 TypeScript 7의 검사를 통과한다. 백엔드 패키지의 잠금 버전은 변경하지 않았다.

Node.js 22에서 타입 검사와 프로덕션 빌드, 기존 회귀 검사 13개가 통과했다. 별도의 Compose 프로젝트와 빈 의존성 볼륨에서도 `npm ci --include=dev`부터 개발 서버 기동까지 확인했다. Vite 자동 재빌드와 Node 자동 재시작, 실제 Traefik을 통한 앱의 HTTP 200 응답을 확인했다. Chromium에서 1440/1024/390/320px와 라이트/다크 테마의 레이아웃 64개, 실제 컨테이너 로그 163개, 로그인·설정 저장·Jobs·Exec 등의 기능 28개 검증을 통과했다. 검증 코드는 임시 경로에만 작성했다.

Compose 검증은 앞 절과 동일한 클라우드 오버라이드를 사용했다. 원본 Dockerfile의 외부 설치 단계와 신규 원격 저장소의 전체 빌드·배포는 이번 검증에 포함하지 않았다.
